# Лабораторная работа №12 — аутентификация и сессии

В проекте представлены по одному заданию из каждого уровня сложности. Это учебное приложение на Node.js/Express с серверной сессией в HttpOnly cookie; роли и доступы проверяются сервером.

## Реализованные варианты

1. **Базовый, №1:** форма входа в кабинет студента, сообщения об ошибке, защищенный список занятий и выход.
2. **Средний, №8:** роли `student` и `teacher`; endpoint кабинета преподавателя доступен только роли преподавателя.
3. **Повышенный, №16:** административный API со списком пользователей, проверкой роли и журналом успешных/неуспешных входов и выходов.

Один сервер демонстрирует все три задания, а интерфейс показывает раздел, соответствующий вошедшей роли. Например, запрос студента к `/api/teacher/summary` вернет `403`, а запрос без входа к защищенному endpoint вернет `401`.

## Запуск

Требуется Node.js 18 или новее.

```bash
cd LAB12
npm install
# Создайте случайный секрет для локального запуска:
export SESSION_SECRET="$(node -e \"console.log(require('crypto').randomBytes(32).toString('hex'))\")"
npm start
```

Откройте http://localhost:3000. В PowerShell секрет можно задать командой `$env:SESSION_SECRET = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))`.

## Демонстрационные аккаунты

Это фиктивные локальные учетные записи для демонстрации; не используйте указанные пароли в других системах.

| Логин | Пароль | Роль |
|---|---|---|
| `student` | `Student123!` | student |
| `teacher` | `Teacher123!` | teacher |
| `admin` | `Admin123!` | admin |

Пароли хешируются bcrypt при запуске и не сохраняются в виде открытого текста в хранилище пользователей. Реальные пароли и токены в проект не добавлялись.

## Проверка требований и сценарии

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Вход с корректными данными | Успех, серверная сессия создана |
| 2 | Неверный пароль | `401`, показано сообщение об ошибке |
| 3 | Пустые поля | Браузер блокирует отправку; API возвращает `400` |
| 4 | Запрос `/api/student/lessons` без входа | `401 Unauthorized` |
| 5 | Выход, затем повторный запрос защищенного API | Сессия удалена, endpoint возвращает `401` |
| 6 | Бездействие дольше 15 минут | Cookie истекает, защищенный запрос возвращает `401` |
| 7 | Студент обращается к `/api/teacher/summary` | `403 Forbidden` |
| 8 | Обновление страницы после входа | `/api/auth/me` восстанавливает пользователя по cookie сессии |

Дополнительно проверьте, что администратор открывает `/api/admin/users` и `/api/admin/audit`, а другие роли получают `403`.

## Безопасность и ограничения учебного прототипа

- Cookie сессии имеет `HttpOnly`, `SameSite=Strict`, ограниченный срок жизни; `Secure` включается при `NODE_ENV=production` (для production обязательно HTTPS).
- При успешном входе идентификатор сессии меняется; выход уничтожает сессию на сервере и удаляет cookie.
- Защищенные API проверяют вход и роль на сервере; скрытие элементов интерфейса не считается защитой.
- Пароли проверяются по bcrypt-хешу. JWT и OAuth/OIDC в этом варианте не используются: выбран подход серверной сессии.
- Для простоты используется хранилище сессий Express по умолчанию (память процесса) и временные данные. Они очищаются при перезапуске; такое хранилище не подходит для production или нескольких серверов.
- В production следует подключить постоянное хранилище сессий и пользователей, TLS, CSRF-защиту с токеном для соответствующей модели развертывания, ограничение попыток входа и управление секретами. Не выставляйте учебный сервер в публичную сеть.

## Дополнительная мера

Журналируются успешные и неуспешные входы и выходы; журнал доступен только администратору и ограничен последними 100 событиями. Это демонстрирует аудит, но хранится только в памяти и не является долговременным журналом безопасности.
